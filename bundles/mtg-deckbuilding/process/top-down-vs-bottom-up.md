# Definition

**Top-down** design starts from a problem or fantasy (“cheat big creatures into play”) and decomposes it into strategies and cards. **Bottom-up** design starts from concrete pieces (a precon, a binder legend, prerelease pulls) and stitches them into a coherent system.[^341-build]

Neither is better. Confusion comes from mixing them silently—e.g. forcing a pet commander into a top-down plan that needs different colors or a different engine.

# Top-down

* State the problem or fantasy first; several strategies may solve it (reanimator *or* ramp for “cheat fatties”).
* Derive [deck vision](/commander/deck-vision.md), then search for a commander that enables the plan.
* Packages and category budgets fill roles that serve the vision.

# Bottom-up

* Start from a fixed commander, precon core, or must-include cards.
* Commander choice is often already a bottom-up decision—“I want to play this card.”
* Job is linkage: which packages make those parts into one [game plan](/foundations/game-plan.md)?

# Guidelines

* Name which mode you are in before cutting or adding cards.
* Top-down builders should resist jamming unrelated pet cards; bottom-up builders should resist stretching a cool card into a plan it does not support.
* Both paths can converge on the same list; the path only changes the order of decisions.[^341-build]
